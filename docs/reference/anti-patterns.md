# Anti-Patterns

常见失败模式及识别方法。当 agent 行为匹配下列模式时，应立即纠正。

## Engineer 反模式

| 反模式 | 表现 | 纠正 |
|--------|------|------|
| **过度设计** | 为"将来可能需要"设计抽象层、插件系统、配置中心 | 只设计当前需求+1 个已知扩展点，砍掉其余 |
| **不读代码就设计** | 方案与现有代码结构格格不入，重新发明已有模块 | 先花 5 分钟读相关源码和测试，再写设计方案 |
| **瀑布式拆解** | 把任务拆成 20 个步骤，每步 2 行代码 | 合并相关步骤，一个 coder 任务应该是 1-3 个文件的连贯改动 |
| **忽略边界条件** | 设计只覆盖 happy path，不提错误处理、空值、超时 | 每个接口/数据流都标注失败模式 |

## Coder 反模式

| 反模式 | 表现 | 纠正 |
|--------|------|------|
| **范围蠕变** | "趁改这个文件，我把命名统一了" | 只改设计文档列出的文件和逻辑 |
| **盲从实现** | 发现设计明显有问题但心想"设计肯定有道理"继续写 | 暂停，列出具体问题，反馈给 engineer |
| **跳过验证** | 代码改了但没跑，心想"改这么简单不会有问题" | 每次改动后运行最小验证：编译、相关测试、手动检查 |
| **猜测模糊点** | 设计说"处理错误"但没写怎么处理，自己随便选一种 | 先查现有代码的惯例；无惯例时列出选项和默认选择 |

## Orchestrator 反模式

| 反模式 | 表现 | 纠正 |
|--------|------|------|
| **为小事启动** | 改一个 typo 也要走 engineer→coder 流程 | 判断标准见 engineer skill 的"何时使用" |
| **brief 太模糊** | "实现删除功能"就一句话交给 coder | brief 必须包含：目标、验收、涉及文件、约束、验证命令 |
| **不回看** | coder 实现完后不跟 brief 对照验收 | 逐条检查 acceptance checks，标注偏差 |
